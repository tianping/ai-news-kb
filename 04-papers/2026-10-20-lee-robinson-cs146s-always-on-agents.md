## 概述

终端里的 harness（模型循环调用工具、读结果、决定下一步）一合上电脑就停了。**常驻智能体**把这个循环搬到服务器和云端：状态持久保存、任务能继续、随时可被唤醒；空闲时进程和电脑都休眠。它像一位同事，在后台干活，有重要进展再汇报。目标是让它持续处理**几周甚至几个月**的工作。

## 一、AI 辅助开发的四个阶段

1. 从 ChatGPT 复制粘贴代码；
2. 模型配合简单 harness 自己改文件、跑 shell（终端协作，Cursor tab 补全）；
3. 编程智能体有了专门应用，可以多个并行、部分上云，但**人仍是瓶颈**，要逐条审批命令；
4. **现在**：智能体有自己的电脑、记忆和技能，在你睡觉时继续推进。

- 人的角色变成**边干边引导**：中途插一句「其实周四再做」，模型能理解前后消息的关系。
- **自动审查**：发邮件、发 Slack、执行 shell 前，由**另一个独立模型**审查。作者认为对几百条命令逐条审批的人容易疲劳，模型往往做得更好。
- 反直觉的一点：**模型越强，界面可以越简单**，越来越像给同事发消息。

## 二、让常驻智能体成立的六项模型能力

1. **长时间遵循指令**：配合上下文压缩（对越来越长的对话做摘要），可连续运行数小时到数天。
2. **子智能体**：子智能体有全新的上下文窗口，去做大量工具调用，只把结果带回主智能体。
3. **可靠的工具调用**：作者认为工具调用的幻觉问题已大体解决。
4. **Computer use**：在 Linux 电脑上开浏览器、点屏幕，处理没有 API/MCP 的网站。
5. **知识存进文件**：读、搜、取回。
6. **从演示中学习**：看你做一遍，整理成技能、记忆或例行任务。

**一切皆文件**：
- **用户资料**：协作需要知道的事实，例如「用户喜欢全小写发消息」，每次都放进提示词；
- **带日期的工作日志**：可以回答「我上周做了什么」；
- **技能**：Markdown 写清步骤和成败标准（如怎样写好邮件、怎样设计 API），可分享，GrokBot 有插件系统；
- **例行任务**：像 cron，按时间表运行一段提示词。

## 三、系统内部

**触发 → 唤醒 → 工作 → 休眠**
- 触发源：用户消息、Slack @、电话、会议、后台任务完成、定时任务。在 SpaceX，越来越多员工让 Bot 代为参会、记笔记再汇报。
- 事件先**路由、去重**，进入合适的对话，再由规则判断「现在要不要告诉用户」。别像每做完一点就跑来报告的同事，有些事一天汇报一次就够。
- 只有需要浏览器或桌面时才启动云端电脑；对话、记忆、例行任务存在数据库和存储里。原因是给每人一台常开的电脑太贵。（整理者注：所以 Agent Sandbox 成了热门投资方向；Meta Muse 给每个用户配了一台电脑。）

**三块架构**：应用与消息入口 ｜ **Agent Loop Server**（收消息 → 入队 → 模型循环调用工具 → 存状态）｜ **Agent Computer**（Firecracker 虚拟机：文件、命令、Chrome、虚拟桌面，可快照、关机、恢复，用户可连进去实时看、亲自操作；多个 Bot 各分一块屏幕）。
- **瘦客户端、厚服务器**：服务器代码能快速更新，不用等应用商店审核。
- **关键：循环和虚拟机分开**。循环放在虚拟机里，就没法关机还让智能体继续跑。比如打 Linux 零日补丁要重启虚拟机，循环和状态要保留。

**持久工作流**
- 客户端发送 → 服务器确认 → 开始一轮 → 工具结果入库 → 客户端订阅变化信号再拉取；需要去重，避免重试导致同一条消息出现多次。
- 普通队列在第 3 步故障后可能从头重来；**持久工作流保存执行进度，从第 3 步继续**。他们用开源的 **Temporal**（基础设施仍需自己运行）。
- **优先级**：用户直接说的修正优先，必要时暂停当前循环；群聊、别人的 Slack、后台例行任务排队；短时间内连发的三四条消息合并成一轮处理。

## 四、工具与助手

- **只有一个面向用户的通信工具 `SendToUser`**。手机、桌面、邮件、Slack 共用；客户端自己决定怎么呈现：登录表单（接 1Password）、支付（Stripe Link、X Money）、发信前给草稿让用户编辑批准，有时回一个表情就够了。服务器上仍有很多其他工具（shell、读文件、调云端智能体、录屏、做演示）。
- **动态工具发现**（工具搜索工具）：先只给工具名，需要时再加载 schema 和说明。避免 Gmail、Drive、YouTube 等 MCP 的工具定义一次性塞满上下文。
- **工具选择阶梯**（便宜可靠的在前）：已有对话信息 → 插件、MCP、API（如 Plaid 查银行）→ 网页搜索 → 浏览器 → 整个桌面（跑脚本、命令、现场构建）→ 请用户帮忙。**连接器失效时要告知用户，不要绕开连接器改用浏览器。** 用浏览器时优先读 HTML 或无障碍树，少用截图省 token；遇到双重验证、人机验证就请用户介入。阶梯只说怎么拿信息，授权操作仍要审批。
- **主智能体保持轻量**：大量 shell、截图、昂贵的工具调用交给 helper（子智能体），只带回结果。「无限上下文」不存在，靠分工和上下文管理减少撞到上限的次数。每个 helper 各有自己的持久工作流，崩了能恢复；主智能体像管待办清单的同事，可以查看进度、调整、叫停助手。
- **工具设计细节**：
  - 一轮执行中别增删工具，描述和 schema 尽量精简；
  - 如果模型 90% 的 shell 调用在做同一件事，就给它做一个专用工具，更高效也更好检查；
  - **错误信息要告诉智能体下一步怎么办**，不要只写「发生错误」。
- **安全**：虚拟机隔离不能解决一切。还需要：执行 shell 前由独立模型自动审查；邮件、网页、webhook 内容保留**来源边界**，钓鱼邮件被读到也不能变成用户指令；不可撤销的操作（如发邮件）先问用户；密码走专门流程，不进对话。

## 五、上下文工程：省钱与记忆

- **稳定前缀命中缓存**：工具定义、系统提示词放前面、保持不变，新消息追加在后面。**不必要的 cache miss 当作缺陷来排查。**
  - 作者点名：今年一月 **OpenClaw** 爆火，人们用模型商的订阅套餐来跑它，这种新用法当时没被优化，出现大量 cache miss，需要工程修复。
  - 技巧：提示词各段顺序固定；做 A/B 测试时别打乱其他稳定段；**给每段算哈希**来定位哪段变了；用户打开窗口或开始打字时就**预热缓存**（类似鼠标悬停时预取下一页）。
- 长工具输出写进文件，按需读取；截图类重活交给 helper；对话持续修剪。
- **趁缓存还有效时做摘要**：缓存窗口约 10–60 分钟。用户离开后，趁长对话仍命中缓存时便宜地压缩，30 分钟后回来从摘要接着聊。不是定时压缩，而是利用缓存窗口挑时机；摘要是有损的，作者觉得怎么压缩不丢重点够做一个博士课题。
- **记忆分层**：
  - 每次都带的核心事实（如全小写偏好，不遵守会显得很怪）；
  - 按相关性取舍的其他事实（像垃圾回收，也像人脑的工作记忆）；
  - 带日期的日志；
  - 只管接下来半小时、一小时的临时笔记；
  - 其余放文件，需要时检索。

## 六、模型与产品一起进步

- SFT 阶段让模型看 harness 的实例、熟悉工具；RL 阶段训练遵循指令、从数百项技能里选对、在浏览器里点对。
- **不同角色优化目标不同**：主智能体要快（优化延迟）；长任务助手花 10 分钟还是 12 分钟差别不大。
- **两个改进循环**：
  - 内循环（几乎每天）：调错了工具 → 变成一项评测 → 修 harness、提示词、bug 或推理 → 评测通过后发布；
  - 外循环：训练新模型，从过去的失败中学习，再验证是否真的变好；新能力带来新用法，例如多个 Bot 在群聊里协作。
- **「删掉产品」原则**：假设今天的模型是未来最差的一代。六个月后，为弥补模型短板而加的结构可能要拆掉、界面要重做。为下一代模型做产品：尽量少做也能工作。
- **6–12 个月判断**：
  - 持续工作从数小时、一天延长到几周、几个月；
  - 更会从过去的对话里找信息，记忆的表示可能是文件、图或其他形式；
  - 工具更多，像给新同事配工作环境；
  - 界面更简单，可能是语音，或 Jony Ive 参与设计的那类新设备；
  - 在工作中学技能并存成文件，人和公司也更善于把工作方法写下来给智能体用。
- **未解决的问题**：
  - 长期任务怎么评测（任务跑一个月，模型每月一更）；
  - 记忆与安全（记住对的东西、保护 harness、防恶意输入接管）；
  - **什么时候安静、什么时候打扰**（「你昨天没来上课，我录了音做了笔记」可能很有用，也可能很烦）；
  - 多智能体共享电脑和记忆时怎么协调；
  - 长期运行的成本，token 流量会显著增加。
- **新一代产品的基础组件**：持久工作流、沙箱、云端电脑、记忆、技能、服务连接器，加上语音、支付、身份、评测、可观测性。引 OpenRouter 的 Alex：这像 2005 年的网页应用，大家都有服务器、数据库、CRUD 界面，组件相似不代表产品只能做同一件事。每个新产品要么整合智能体能力，要么变成供其他智能体用的数据。

## 给工程师的三条建议

1. **认真理解系统架构**。代码越来越好写，但架构决策的影响会累积；作者自己仍会读代码，弄清发布出去的系统到底怎么工作。
2. **亲手做一个版本**：在课上的基础 harness 上加服务器、沙箱、虚拟机、记忆、助手和适合自己的界面。
3. **别回避学 LLM 原理**，就像做网页应用要懂数据库一样。
