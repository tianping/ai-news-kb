## 1. Agent = 与环境持续交互

- 经典定义（Russell & Norvig《AIMA》）：**感知环境 + 对环境采取行动**。
- 放到 LLM 系统里：
  - **环境**：代码仓库、网站、应用、业务流程；
  - **观察**：读到的文件、网页、截图、工具结果；
  - **动作**：编辑文件、跑命令、调 API、点按钮；
  - **评价信号**：测试是否通过、输出是否满足要求、用户是否认可。
- **两个开场案例**：
  - **能力**：Nicholas Carlini（Anthropic）的实验，16 个并行 Agent 用两周写出约 10 万行 Rust 的 C 编译器，能编译 Linux 内核。
  - **风险**：Summer Yue 要求「行动前先审批」，Agent 却继续删邮件，最后靠杀进程才停下来。Daniel 推测是**上下文压缩后丢了「不要删邮件」这条指令**。
  - 结论：能做多少看能力，允许它独立做什么则涉及权限、信任和后果。读文件、发邮件、迁移支付接口，执行边界各不相同。

## 2. 模型怎么调用工具

- 工具调用仍是 next-token 预测，只是生成的是**结构化内容**：调哪个工具、传什么参数。例：`read_file(path="test.py")`，用调用 ID 关联调用和结果。
- **分工**：模型只生成动作的表示，**harness（运行控制层）**负责解析、校验参数、执行、把结果放回上下文。
- ⚠️ 「模型回答说读过文件」和「系统真的执行了读取」是两回事。要判断 Agent 做了什么，**必须查看它的工具调用和执行结果**。

## 3. 行动循环

1. 把任务、可用工具和历史交给模型；
2. 模型选下一步动作；
3. harness 执行，拿到结果；
4. 结果加入上下文，继续判断，直到任务结束。

- 这就是 ReAct「推理与行动交替」的基础。mini-swe-agent 的精简代码演示了这个循环：初始化消息 → 反复查询模型、执行动作 → 追加输出和观察。自己实现时还要加**终止条件、错误处理、资源限制**。
- 课堂示例：
  - **SWE-bench 轨迹**：退出码 0 只说明这条命令成功了，任务有没有解决要看最终测试。
  - **OpenHands 做 Flask 待办应用**：查日志发现端口被占 → 换方式启动 → 打开浏览器测试增删。关键在于读懂反馈、调整下一步。

## 4. 长任务需要的六项能力，两条建设路径

两条路径：
- **模型训练**：预训练、SFT、RL；
- **harness 工程**：提示词、工具、记忆、控制流程、校验、重试、执行边界。

Graham 的个人看法：很多问题先用系统工程解决，足够重要了再专门训练。他偏好有条件时用训练解决，但长上下文的计算效率、用户定制等仍需要工程，没有哪条路始终更好。

| 能力 | harness 工程 | 模型训练 |
|---|---|---|
| **工具调用**（选对工具、给对参数） | 语法约束解码、参数校验 | 工具调用轨迹 SFT |
| **长上下文连贯**（做久了仍记得关键约束） | 压缩、动态检索记忆、委派给子 Agent | 长上下文 SFT |
| **可定制**（用户偏好、领域规则） | 记忆、skills、自定义工具 | 从用户反馈 RL |
| **复杂任务管理** | 规划、分解、子 Agent 委派，加上**验证**（子任务完成后要检查能否支撑整体目标） | 长时程任务训练 |
| **环境理解**（代码库、网页、截图形式不同） | 带领域知识的 skills | 符合实际观察形式的 SFT，特定环境 RL |
| **安全** | 工具执行沙箱、凭证访问限制、轨迹监控 | 考虑安全的 RL |

- 安全约束要**落实到执行链上**：在动作发生时约束能访问哪些文件、调用哪些接口、何时需要审批。只靠模型「记住」的限制，在长任务里很脆弱（见删邮件案例）。

## 5. 完整 Agent 系统的组件

- **模型**：生成判断和动作；
- **harness**：管理状态、工具、记忆、控制流，处理参数校验、执行错误、权限；
- **沙箱**：隔离执行，限制计算、网络、文件系统，提供可复现环境；
- **推理服务**：批处理、缓存复用、流式、并行、吞吐；
- **训练系统**：数据、轨迹收集、训练、检查点、评估；
- **可观测性与监控**：记录轨迹和指标，追踪质量、费用、失败。

**排障思路**：任务没完成时，把问题落到具体组件上——模型选错了动作？历史没组织好？工具执行出错？还是最终结果没有验证？

## 6. 动手：从一个小循环开始

1. **先让一次调用完整发生**：只接 `read_file` 一个工具，走完「任务 → 调用 → 执行 → 观察 → 回复」；保留每一步消息，检查回答是不是真的依据工具返回的内容。
2. **再让表现可测量**：选一组任务、定义成功条件、记录通过与失败，看失败出在哪一步（工具、参数、上下文、执行、最终判断）。
3. **最后根据失败改进**：先改工具说明、记忆组织、控制流；有条件再训练。比较改动前后的结果、成本和稳定性。
